# 3D3S 云授权系统 —— 方案设计

> 面向前端与后端实现者。说明系统怎么分层、数据怎么建模、权限怎么落地、闭环怎么保证一致。

---

## 1. 总体设计原则

| 原则 | 具体做法 | 解决什么问题 |
| --- | --- | --- |
| **组织是第一公民** | 所有业务对象都挂 `orgId`，没有任何对象直接归属自然人 | 个人版最根本的错误就是资产归属错位 |
| **账目只算不存** | 席位「已分配数」永不落库，实时由生效中的分配记录聚合 | 席位数对不上是这类系统最典型的线上事故 |
| **审批链随单走** | 审批链在提交时快照进单据，而非读全局配置 | 配置变更不污染历史单据 |
| **权限声明式** | 角色 → 权限点 → 菜单/路由/按钮三处统一消费同一份声明 | 避免"菜单藏了但接口能调"式的假权限 |
| **后果前置告知** | 每个破坏性操作在确认前说明具体后果与数字 | B 端操作代价高，误操作成本由企业承担 |

## 2. 分层结构

```
src/
├── domain/                  纯领域层，无 React 依赖
│   ├── types.ts             全部实体与联合类型（唯一事实来源）
│   ├── permissions.ts       权限点定义、角色→权限映射、数据范围
│   ├── navigation.ts        菜单声明（携带权限点）
│   └── seed.ts              种子数据与逻辑基准时间
├── store/
│   ├── appState.ts          纯逻辑：AppState · initialState · selector · reducer（无 React）
│   ├── context.ts           Context 与 AppContextValue 定义
│   ├── AppProvider.tsx      Provider 组件
│   ├── useApp.ts            消费侧 hook
│   └── index.ts             对外唯一入口（页面只从 '../store' 引入）
├── components/
│   ├── layout/              Sidebar（角色驱动）· Header（身份切换）· Layout
│   └── common/              StatusBadge · TabFilter · SearchBar · Modal
│                            · FlashToast · RequirePermission
└── pages/                   15 个页面，只消费 store 暴露的 selector 与 action
```

加上校验脚本：

```
scripts/
├── verify-flows.ts          驱动真实 reducer 走完全部分支（60 项断言）
└── verify-pages.ts          Puppeteer 巡检 4 角色 × 13 路由的渲染与越权拒绝
```

依赖方向单向：`pages → store → domain`。`appState.ts` 不 import React，因此校验脚本能在 Node 里直接驱动它；将来接后端时只需把 reducer 的每个 case 换成接口调用，页面无需改动。

## 3. 数据模型

### 3.1 实体关系

```
Organization ──1:N── Department ──1:N── Member
     │                                    │
     │                                    │ 持有
     │ 持有                                ▼
     └──1:N── SeatPool ──1:N── Assignment ─┘
                 ▲                 
                 │ 到账扩容         
              Order ◀──0:1── Application ──N:1── Member（申请人）
                                   │
                                   └── ApprovalStep[]（内嵌审批链快照）
              
CatalogModule ── 被 SeatPool / Application / Order 引用
AuditLog ── 独立追加，引用 actor 与 target（弱引用，仅存名称快照）
```

要点说明：

- **SeatPool 对 (orgId, moduleId) 唯一**。一个企业对一个模块只有一个池，避免多池带来的"从哪个池扣"的歧义。免费版与商业版是两条独立的 `CatalogModule` 记录，因此天然是两个池。
- **Assignment 是席位的实体化**。池只记 `total`，占用情况由 `status === '生效中'` 的 Assignment 数量决定。回收不删记录，改状态并记 `revokedAt`，保留审计价值。
- **AuditLog 存名称快照而非仅存 ID**。成员改名或删除后，历史日志仍可读，这是合规审计的基本要求。

### 3.2 为什么不做三级组织

企业 → 部门 → 项目组的三级结构会让权限判定从"比较 deptId"变成"判断子树包含关系"，且审批链要支持可变级数。当前用 `Application.projectName` 这个轻量字段承接项目维度的成本归集诉求，成本远低于引入第三层组织。若后续 S-02（项目成本报表）验证了需求强度，再升级为实体。

## 4. 权限落地

### 4.1 三层消费同一份声明

```ts
// domain/permissions.ts —— 唯一声明处
const rolePermissions: Record<Role, Permission[]> = { ... };
export function can(role, permission): boolean
export function canAny(role, permissions[]): boolean
export function scopeOf(role): 'self' | 'dept' | 'org' | 'platform'
```

| 消费点 | 方式 |
| --- | --- |
| 菜单 | `navigation.ts` 每项携带 `permissions[]`，`navFor(role)` 过滤并按组返回 |
| 路由 | `<RequirePermission permissions={[...]}>` 包裹页面元素 |
| 按钮 | 页面内 `can(me.role, 'seat:manage')` 决定可操作或只读 |

同一份声明驱动三处，不存在菜单隐藏但页面可直达的情况。

### 4.2 数据范围的实现

范围过滤集中在 store 的 selector 里，页面不自己写过滤逻辑：

```ts
visibleMembers(state, me)      // self / dept / org / platform
visibleAssignments(state, me)
visibleApplications(state, me)
visibleOrders(state, me)
visibleAudit(state, me)
inboxOf(state, me)             // 当前该我处理的申请
```

这样做的好处是范围规则只有一处可改。页面的责任仅是把范围**显示**给用户（副标题里的"数据范围：结构一所"）。

### 4.3 审批归属判定

`inboxOf` 的判定顺序：

1. 厂商运营 → 只认 `step.role === 'VENDOR_OPS'` 的待办，跨企业
2. 非本企业申请 → 直接排除
3. 待办环节是企业级 → 仅企业管理员
4. 待办环节是部门级 → 企业管理员全收，部门管理员仅限 `app.deptId === me.deptId`

第 4 条让企业管理员可代部门审批，避免所长休假流程卡死；同时部门管理员严格隔离，看不到其他部门的申请。

## 5. 状态管理

### 5.1 为什么用 Context + reducer

需求是"流程必须真跑通"，但不接后端。候选方案：

| 方案 | 评价 |
| --- | --- |
| 静态数据 + 局部 useState | 无法跨页面联动，申请了但审批中心看不到，等于没闭环 |
| **Context + reducer（选定）** | 单一状态树，所有页面读同一份真相；写操作集中在 reducer，便于保证一致性 |
| Zustand / Redux Toolkit | 能力过剩，且引入新依赖 |
| 加 localStorage 持久化 | 演示时容易带入脏状态，且刷新重置反而利于反复走查 |

reducer 承载 20 个 action，覆盖申请、审批、席位、订单、成员、厂商六类写操作。

### 5.2 一致性保障机制

**逻辑时钟**：状态里维护 `now`，每次写操作推进 1 分钟，新记录用推进后的时间。避免用真实时间导致的记录时序错乱（种子数据基准是 2026-03-31，与真实时间相差数月）。

**统一提交出口**：所有 action 通过 `commit(state, ctx, patch, flash)` 收口，保证每次写操作都同时完成三件事——更新数据、追加审计日志、推进时钟。漏写审计在结构上不可能发生。

```ts
function commit(state, ctx, patch, flash): AppState {
  return { ...state, ...patch, now: ctx.now, seq: ctx.seq,
           auditLogs: [...ctx.logs, ...state.auditLogs], flash };
}
```

**席位发放的单一实现**：`fulfil()` 是所有席位入池路径的唯一实现，被三处调用——在线支付到账、厂商确认到账、QUOTA 审批通过。它统一处理"新建池 / 扩容 / 续费"三种情形与"自动分配给申请人"的逻辑，避免三处各写一遍导致行为漂移。

**幂等保护**：`fulfil` 分配席位前检查该成员是否已持有同模块生效中席位，已持有则跳过，避免重复分配。

### 5.3 并发余量校验

SEAT 分支存在提交与审批之间的时间差。审批通过时必须重新校验：

```ts
if (spareSeats(state, pool) < 1) {
  return { ...state, flash: { kind: 'error',
    text: `「${mod.name}」席位已被占满，无法直接分配。请先扩容后再审批，或驳回本申请。` } };
}
```

不做静默降级（比如自动转成采购申请），因为那会绕过企业管理员的付费决策权。

## 6. 关键流程时序

### 6.1 采购分支完整闭环

```
成员            部门管理员      企业管理员                厂商运营
 │                 │              │                        │
 ├SUBMIT_APPLICATION              │                        │
 │ decideKind → PURCHASE          │                        │
 │ steps = [部门, 企业]            │                        │
 │ status = 待部门审批             │                        │
 │                 │              │                        │
 │      DECIDE_APPLICATION(通过)   │                        │
 │      → 下一环节存在 → 待企业审批  │                        │
 │                 │              │                        │
 │                 │  DECIDE_APPLICATION(通过)              │
 │                 │  → 无下一环节 + kind=PURCHASE → 待采购  │
 │                 │              │                        │
 │                 │  CREATE_ORDER(applicationId)           │
 │                 │  → 订单 待支付                          │
 │                 │              │                        │
 │                 │  PAY_ORDER                             │
 │                 │  对公转账 → 待厂商确认（席位未发放）      │
 │                 │              │                        │
 │                 │              │      CONFIRM_ORDER      │
 │                 │              │      → fulfil()         │
 │                 │              │        · 池扩容          │
 │                 │              │        · 分配给申请人     │
 │                 │              │        · 申请置已完成     │
 │◀────────────── 席位在「我的授权」出现 ──────────────────────┤
```

在线支付时 `PAY_ORDER` 直接调用 `fulfil()`，跳过厂商环节。**支付方式是唯一决定厂商是否介入的变量**。

### 6.2 离职释放

```
SET_MEMBER_STATUS(已停用)
  ├─ 成员状态 → 已停用
  ├─ 其全部生效中 Assignment → 已回收（记 revokedAt / revokedById）
  ├─ 审计日志：「停用成员」，详情含回收席位数
  └─ 反馈：「已停用郑凯，释放 3 个席位回池」
```

席位释放是停用的**同一个原子操作**，不依赖管理员额外记得去回收。这是席位池模型相对按人指派的核心价值点，也是场景 B 的直接答案。

## 7. 视觉与交互约定

沿用原有设计语言，未做重新设计，仅扩展：

| 项 | 约定 |
| --- | --- |
| 色板 | Arco 风格，主色 `#1C71D8`；语义 token 定义在 `index.css` 的 `@theme` 中，页面只用 `text-text-muted` 这类语义类名，不散写十六进制 |
| 状态徽章 | `StatusBadge` 统一维护 30+ 文案到 5 种色调（info/success/warning/danger/neutral）的映射，页面不自行决定颜色 |
| 侧边栏 | 深蓝渐变保留；新增按组分区（工作台/企业管理/厂商后台）与审批待办角标 |
| 反馈 | 写操作统一走 `FlashToast`，文案由 reducer 生成（描述实际后果，如"释放 3 个席位回池"），而非页面写死"操作成功" |
| 拒绝页 | 越权时显式渲染而非跳转，让权限边界可见 |

## 8. 验证方式

闭环不靠人工点，两个脚本可重复跑。

```bash
npm run verify         # 流程闭环：直接驱动 reducer，60 项断言
npm run dev            # 另开一个终端
npm run verify:pages   # 渲染与权限：4 角色 × 13 路由，共 52 个组合
```

`verify-flows.ts` 覆盖的分支：

| 走查 | 覆盖点 |
| --- | --- |
| 0 | 权限矩阵、数据范围、部门管理员不越界 |
| 1 | SEAT：池内直接分配，单级审批，池容量不变而占用 +1 |
| 2 | PURCHASE：两级审批 → 下单 → 对公转账 → 厂商确认 → 扩容并自动分配 |
| 3 | QUOTA：三级审批 → 新建池 → 自动分配 |
| 4 | 驳回留痕、申请人撤销 |
| 5 | 停用成员即回收其全部席位，回收记录保留 |
| 6 | 池满时拒绝分配、续费按新数量重置容量并延长到期日 |
| 7 | 审计日志随写操作增长、每条有操作人、逻辑时钟推进 |

`verify-pages.ts` 对每个「角色 × 路由」组合断言两件事：有权限时页面正常渲染且无控制台报错；无权限时**直达 URL 必须被显式拒绝**，而不是静默跳转。

## 9. 接后端时的映射建议

当前 reducer 里的每个 action 对应一个后端接口，迁移路径清晰：

| Action | 建议接口 | 事务要求 |
| --- | --- | --- |
| `SUBMIT_APPLICATION` | `POST /applications` | kind 判定必须在服务端做，客户端判定仅用于提示 |
| `DECIDE_APPLICATION` | `POST /applications/:id/decisions` | 审批 + 席位分配 + 审计需在同一事务；SEAT 分支需对池加行锁 |
| `ASSIGN_SEAT` / `REVOKE_SEAT` | `POST /pools/:id/assignments`、`DELETE /assignments/:id` | 分配需校验余量并加锁 |
| `CREATE_ORDER` / `PAY_ORDER` | `POST /orders`、`POST /orders/:id/payments` | 支付回调需幂等键 |
| `CONFIRM_ORDER` | `POST /orders/:id/confirm` | 到账确认 + 席位入池 + 自动分配同事务 |
| `SET_MEMBER_STATUS` | `PATCH /members/:id` | 停用与批量回收席位同事务 |

三处必须服务端强校验，不可信客户端：
1. **申请分支判定**（决定要不要花钱）
2. **席位余量**（决定能不能分配，需数据库层面加锁防超卖）
3. **审批人资格**（当前环节 role 与操作者身份、部门是否匹配）

## 10. 已知取舍与遗留

| 取舍 | 理由 | 后续 |
| --- | --- | --- |
| 分配权收归企业管理员 | 避免部门间抢占；代价是企业管理员成为瓶颈 | 由 S-01「部门配额」缓解 |
| 免费额度不硬性拦截 | `Organization.freeSeatQuota` 当前是展示与决策参考，厂商审批时未强制卡住上限 | 接后端时应在厂商审批处校验 |
| 用量数据为预置序列 | 无真实埋点，`usageHistory` 与 `Assignment.usedDays` 为构造数据 | 接入客户端心跳后替换 |
| 刷新即重置 | 演示定位，便于反复走查 | 接后端后自然消失 |
| 单一企业视角 | 客户侧固定为「上海云构结构设计研究院」，其余 3 家仅在厂商视角出现 | 多租户切换属厂商侧运维能力，非本期目标 |
| 席位按模块独立占用 | 本期没有客户端心跳，无法判断「同一终端并发」；leveling 需要运行时会话，演示层做了会是假规则 | 接客户端后按 S-06 落地：同用户同主机并发多模块按最高档占 1 席 |
| 席位耗尽硬阻断 | 已实现：池满拒绝分配，审批前复检余量，不产生超额账单（刻意避开 Bentley 式事后计费） | 接后端时对池加行锁 |
