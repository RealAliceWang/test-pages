# 3D3S 云授权系统改版 —— 需求分析

> 本文回答一个问题：把面向个人用户的模块授权系统改成面向设计院的 B 端产品，到底要解决谁的什么问题。
> 结论先行：**原系统缺的不是功能，而是「组织」这个主体**。个人版把「谁能用某个模块」当作用户自己的事，B 端里这件事是企业的资产配置决策。

---

## 1. 改造前的问题诊断

对现有代码与流程的盘点结果：

| 现象 | 原实现 | B 端语境下的问题 |
| --- | --- | --- |
| 用户模型 | 单个硬编码 `currentUser`，`role` 字段是「结构工程师」这类职称 | 职称不是权限。系统无法回答"谁可以替别人开通模块" |
| 授权归属 | 模块状态挂在个人身上（`已开通` / `可申请`） | 企业花钱买的资产记在个人名下，人走了授权就废了 |
| 部门 | 各张表里散落的 `department` 字符串 | 无法按部门统计、无法按部门审批、无法按部门分摊成本 |
| 审批 | 有「审核中」状态，但没有审批人、审批意见、审批链 | 审批不可追溯，出了纠纷无法举证 |
| 采购 | 个人下单支付（支付宝/微信） | 设计院不会让工程师自己刷卡买生产工具，且需要对公转账与发票 |
| 数据 | 12 个静态数组，点击不改变状态 | 流程不闭环，无法验证业务假设 |
| 管理端 | 写了 5 个管理页面但未接入路由 | 已经意识到需要管理侧，但缺少角色与权限的骨架去承载 |

一句话总结：**原系统是一个「许可证查看器」，不是一个「许可证管理系统」**。

## 2. 目标客户与场景

### 2.1 客户画像

以中国境内的钢结构 / 空间结构设计业务方为主，三类典型客户：

| 类型 | 规模 | 组织特征 | 授权诉求 |
| --- | --- | --- | --- |
| 甲级设计院 | 200–500 人 | 按专业所划分（结构一所、结构二所…），项目制并行 | 席位要能在所与所之间调剂；要能按项目归集成本 |
| 钢结构工程公司 | 50–200 人 | 设计部 + 深化部，深化部人多但用的模块集中 | 深化模块要多席位，设计模块要少而精 |
| 工业建筑设计院 | 50–100 人 | 厂房、光伏、变电等专项团队 | 专项模块使用季节性强，希望能灵活增减 |

### 2.2 真实工作场景（驱动设计的关键场景）

**场景 A：投标期人力激增**
某设计院中标前需要 3 天内出方案，临时抽调 4 名工程师参与网架计算。这 4 人平时不用网架模块。
→ 需求：**席位能快速分配，且用完能回收**。按人永久绑定授权的模式在这里是纯浪费。

**场景 B：员工离职**
深化设计师何静离职，她名下的钢构深化商业版席位（年费 9800 元）如果不回收就白扔了。
→ 需求：**停用成员时必须自动释放其持有的全部席位**，并且这件事要留痕。

**场景 C：项目成本归集**
财务要求把软件费用摊到具体项目上。现在只能拿到一张"买了 5 个席位共 24000 元"的发票。
→ 需求：申请时**关联项目名**，统计时能按项目/部门看分布。

**场景 D：所长的授权额度焦虑**
结构一所所长想给新人开通模块，但不知道院里还有没有余量，只能去问总工办。
→ 需求：**席位余量对部门管理员可见**，申请时就告知"池内还有 3 个空闲，通过后立即生效，不花钱"。

**场景 E：续费决策缺依据**
多高层商业版 3 个席位即将到期，总工办不知道该续几个。
→ 需求：**利用率数据 + 闲置成本提示**，让续费时敢于缩减。

## 3. 角色定义与职责边界

四个角色，按「谁为什么负责」划分，而不是按职级：

| 角色 | 现实对应 | 核心职责 | 关键动作 |
| --- | --- | --- | --- |
| **普通成员** | 结构工程师、深化设计师 | 用工具干活 | 浏览模块、提交授权申请、查看自己的席位与到期时间 |
| **部门管理员** | 所长、部门经理 | 对本部门的资源使用负责 | 一级审批、查看本部门席位占用与用量、本部门审计 |
| **企业管理员** | 总工办、信息中心 | 对企业采购与合规负责 | 二级审批、席位分配与回收、成员管理、下单支付、全企业统计与审计 |
| **厂商运营** | 见筑云授权运营 | 对平台侧交付与风控负责 | 免费额度审批、对公转账到账确认、模块上下架与定价、企业账号管理、平台看板 |

### 边界的三条原则

1. **成员不碰钱，也不碰别人的授权。** 成员只能为自己申请 1 个席位，不能自行采购。
2. **部门管理员只有一级审批权和只读的管理视图。** 分配与回收席位属于企业资产处置，收归企业管理员。这样做的代价是企业管理员会成为瓶颈，收益是避免部门间互相抢占席位——对 200 人规模的设计院，这个取舍是划算的。
3. **厂商不介入企业内部审批。** 厂商只在两个点上有权：免费额度的核定、对公转账的到账确认。它看不到也不该看企业内部谁给谁分配了席位。

## 4. 授权模型的选择

### 4.1 为什么是席位池

四种候选模型的比较：

| 模型 | 机制 | 优点 | 致命问题 |
| --- | --- | --- | --- |
| 按人指派 | 管理员直接给某人开某模块 | 最简单 | 人员流动即浪费；无法回答"我们还剩多少" |
| **席位池（选定）** | 企业持有 N 个席位，管理员分配/回收 | 资产归企业；余量可见；可调剂；离职即释放 | 席位可能闲置；需要管理动作 |
| 浮动许可 | 按并发数控制，登录抢占退出释放 | 利用率最高 | 抢不到就干不了活，投标期会打架；可视化抽象，说不清"我有什么" |
| 代币池 | 统一代币按用量扣减 | 最灵活 | 用户无法预判花费，采购部门无法编预算 |

选席位池的核心理由：**它是唯一同时满足"资产归企业"和"余量可见"的模型**，而这两点正是原个人版最缺的东西。行业验证见 [竞品分析](./01-竞品分析.md) 第 5 节。

### 4.2 席位池的已知缺陷与本方案的应对

| 缺陷 | 应对 |
| --- | --- |
| 席位闲置浪费 | 席位池页面显式计算**闲置席位数与对应年费**，并在利用率 < 50% 时提示"续费可考虑缩减"；续费弹窗支持减少席位并直接显示节省金额 |
| 部门间抢占 | 分配权收归企业管理员，部门管理员只有申请与只读权；申请时携带项目名与理由，便于裁决 |
| 回收纠纷 | 每次分配/回收写入审计日志，记录操作人、时间、对象；回收前二次确认并明确告知后果 |
| 到期断档 | 30 天内到期的池在工作台与席位池页高亮预警；成员侧在剩余 ≤ 15 天时提示申请续期 |

## 5. 需求清单（MoSCoW）

### Must have（本期必须，已实现）

| 编号 | 需求 | 涉及角色 |
| --- | --- | --- |
| M-01 | 组织 → 部门 两级结构，成员归属唯一部门 | 全部 |
| M-02 | 四角色权限矩阵，菜单与数据范围随角色收敛 | 全部 |
| M-03 | 席位池：持有、分配、回收、到期 | 企业/部门管理员 |
| M-04 | 授权申请三分支自动判定（池内分配 / 采购扩容 / 免费额度扩容） | 成员 |
| M-05 | 多级审批链，含审批人、意见、时间的完整留痕 | 管理员、厂商 |
| M-06 | 采购闭环：下单 → 支付 → 到账 → 席位入池 → 自动分配给申请人 | 企业管理员、厂商 |
| M-07 | 对公转账需厂商确认到账后席位才生效 | 厂商 |
| M-08 | 停用成员自动回收其全部席位 | 企业管理员 |
| M-09 | 操作审计日志，覆盖审批/席位/订单/成员/厂商五类动作 | 管理员、厂商 |
| M-10 | 席位利用率与闲置成本统计 | 管理员 |
| M-11 | 续费可增减席位数并延长有效期 | 企业管理员 |
| M-12 | 身份切换，用于验证四角色视图差异 | 演示需要 |

### Should have（下一期）

- S-01 部门配额：企业管理员给部门设席位上限，部门内自主分配（可缓解企业管理员瓶颈）
- S-02 按项目的成本分摊报表（当前只采集了项目名，未做聚合；竞品均只按组织分账，这是差异化机会）
- S-03 到期批量续费与到期前自动提醒（邮件/短信）
- S-04 成员批量导入与 SSO 对接
- S-05 发票与合同管理
- S-06 leveling：同一人同一终端并发多模块时按最高档占位，而不是逐模块累加（Altair / PKPM 客户心智；本期席位仍按模块独立占用）

### Could have

- C-01 席位使用时段分析（识别可共享的低频席位）
- C-02 浮动席位与固定席位混合模式
- C-03 跨企业集团账号（母子公司席位共享）

### Won't have（明确不做）

- W-01 三级组织（企业→部门→项目组）：两级已覆盖主要场景，三级会显著增加权限判定复杂度
- W-02 成员自行支付：与 B 端采购流程冲突
- W-03 模块内容与计算能力相关的任何改动：本次只改授权体系

## 6. 关键用户旅程

### 旅程一：席位池内有余量（最高频，约占 70%）

```
成员 张思远                部门管理员 赵国栋
  │                            │
  ├─ 模块中心看到「基本分析」     │
  │  提示：池内 7 个空闲席位      │
  │  仅需部门审批                │
  ├─ 提交申请（关联项目+理由）───▶│
  │                            ├─ 审批中心看到申请
  │                            │  上下文：企业席位 5/12，空闲 7
  │                            │  提示：通过后立即分配，不产生费用
  │                            ├─ 通过
  │◀── 席位已分配，我的授权可见 ──┤
```
关键设计点：申请人在**提交前**就知道这条路不花钱、只需一级审批。审批人在**决策时**就看到余量，不用另开页面查。

### 旅程二：商业版席位已满，需采购（金额相关，约占 20%）

```
成员 孙浩         部门管理员 赵国栋      企业管理员 王振华        厂商 沈涛
  │                    │                     │                   │
  ├─ 提交申请 ────────▶│                     │                   │
  │  （提示：需两级审批）├─ 通过，上报 ──────▶│                   │
  │                    │                     ├─ 通过 → 待采购      │
  │                    │                     ├─ 下单（对公转账）    │
  │                    │                     ├─ 提交转账凭证 ─────▶│
  │                    │                     │                   ├─ 确认到账
  │◀────────── 席位入池并自动分配给申请人 ──────────────────────────┤
```
关键设计点：**支付方式决定是否需要厂商介入**。在线支付即时到账；对公转账走厂商确认，这是国内 B 端的真实形态。

### 旅程三：免费模块额度用尽（体现厂商角色，约占 10%）

```
成员 徐磊        部门管理员         企业管理员         厂商运营
  │                 │                  │                 │
  ├─ 申请「多高层」  │                  │                 │
  │  免费池 6/6 已满 │                  │                 │
  ├───────────────▶├─ 通过 ─────────▶├─ 通过 ────────▶├─ 核定额度
  │                 │                  │                 ├─ 批准
  │◀──────────── 免费席位发放并自动分配 ─────────────────────┤
```
关键设计点：免费额度不是无限的，厂商需要控制赠予规模。这条链最长（三级），但因为不涉及付款，反而比采购链更快。

## 7. 成功判据

改版是否成功，用这几个问题检验：

1. 企业管理员能否在 10 秒内回答「我们还有几个空闲席位」？
2. 员工离职后，他的席位是否**必然**被回收，而不依赖管理员记得去操作？
3. 一条授权申请从提交到生效，全过程是否可追溯到人、时间和意见？
4. 续费时，管理员是否有数据支撑"该续几个"的判断？
5. 四个角色登录后看到的菜单和数据范围，是否都符合其职责且不多不少？

以上五问在当前实现中均可正面回答，验证路径见 [PRD](./03-PRD.md) 第 8 节的走查脚本。
